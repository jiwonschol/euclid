# 루프: 축구다움 (match-realism)

> 6칸 정본. 두 번째 주행은 이 파일을 읽고 시작한다 — 심문을 반복하지 마라.
> 작성 2026-07-29 · 브랜치 `claude/loop-harness` (기반 `feature/continuous-match-engine`)
> 이 파일은 루프가 수정할 수 없다(`guard.mjs` 해시 고정).

## 왜 이 루프가 존재하는가

기존 게이트 8종(`sim:match`·`pos`·`play`·`rules`·`stance`·`seq`·`stability`)이 **전부 초록인 상태에서**
화면에는 `수원#의` 가 새어 나오고, 22명이 한 덩어리로 몰려다니고, 경기당 골이 8.7 이었다.
초록 게이트는 "안 나빠졌다"를 재지 "축구로 읽히는가"를 재지 않는다.
이 루프의 첫 임무는 개선이 아니라 **그것을 재는 눈금을 만들어 현재를 빨간불로 만드는 것**이었고, 그건 끝났다(종합 18.8%).

## 2. 연출대 — 임의의 상태를 재현하고 산출물로 굳히는 법

```bash
node sim/report.mjs --round <N> --seed 3 --policy good
```

→ `.claude/loop/runs/round-<N>/` 에 `report.md`(중계 전문·통계·공간 관측) · `pitch-*.png`(스냅샷 6장) · `MANIFEST.json`

- **한 줄 재현** — 위 명령 하나. 시드·정책만 바꾸면 임의의 경기에 도달한다.
- **결정론** — 엔진이 시드 RNG 전용(`Math.random` 금지). 피치 렌더러(`sim/pitchshot.mjs`)는 node 내장 zlib 만 쓰고
  브라우저·캔버스·외부 패키지에 의존하지 않는다. 같은 상태 → 바이트 단위로 같은 PNG.
- **상태 비오염** — 매 호출이 새 `createMatch` 인스턴스. 회차 간 상태가 이어지지 않는다.
- **거짓 성공 불가** — 이게 핵심이다:
  - 출력 디렉터리를 **먼저 완전히 비운다**. 실패한 회차 산출물이 성공한 회차 옆에 섞이지 않게.
  - 같은 시드로 **한 번 더 돌려** 스코어·틱·피드 길이가 같은지 사후 확인한다. 다르면 종료코드 2.
  - 스냅샷마다 요청한 순간과 실제 포착한 순간을 함께 기록하고, 못 잡은 조건은 `missingShots` 로 남긴다.
  - **종료코드로 원인을 구분한다** — `1` = 내 지시가 틀림(포착 조건 불성립), `2` = 환경/엔진이 흔들림(비결정론).
    이 둘을 뭉뚱그리면 오타 하나가 "환경 문제"로 밤새 반복 보고된다.

### 뷰어 캡처 (두 번째 모달리티, 매 회차 1회 필수 — 생략 금지)

헤드리스 렌더러는 **시뮬 상태**를 그린다. 유저가 실제로 보는 것은 `viewer.html` 이고 **둘은 실제로 달랐다.**

2026-07-29 실측: 헤드리스는 936×640 으로 정상적인 피치를 냈지만, 같은 순간 뷰어의 피치 캔버스는
**483×31 CSS 픽셀 = 화면의 1.64%** 였다(백킹 스토어는 820×560). 105×68m 경기장이 종횡비 15.6:1 띠로
눌려서 22명이 31픽셀 높이 안에 들어간다. 게다가 BUILDUP 구간에는 피치가 아예 안 그려진다(`hidePlayers`).

**헤드리스만 봤다면 루프는 "판은 괜찮다"고 판단하고 밤새 엔진 수치만 만졌을 것이다.**
산출물을 한 경로로만 포착하면 그 경로가 못 보는 결함은 영원히 안 보인다. 그래서 이 캡처는 선택이 아니다.

```
preview_start {name: "euclid-proto"}
navigate  http://localhost:8642/viewer.html?seed=3&pauseAt=600
javascript window.__capture            → { ready, clock, requested, seed, ticks } 확인
computer  {action: "screenshot"}
```

**거짓 성공 불가**: `window.__capture.ready` 가 true 이고 `clock` 이 `requested` 와 ±1초 안일 때만 유효한 캡처다.
아니면 로딩 중 화면이나 직전 상태를 이번 회차 그림으로 보고하게 된다.

캡처와 함께 **반드시 기하도 측정한다** (숫자가 없으면 "작아 보인다"는 지적이 되지 않는다):
```js
const r = document.getElementById('pitch').getBoundingClientRect();
({ w: r.width, h: r.height, ratio: r.width / r.height, pctOfViewport: 100*r.width*r.height/(innerWidth*innerHeight) })
```
목표: 종횡비 105/68 ≈ **1.54 ± 0.15**, 화면 점유 **≥25%**.

캡처 실패는 **회차 실패가 아니라 "환경 흔들림"으로 따로 보고**한다. 헤드리스 산출물로 회차를 진행하되,
아침 보고서에 "뷰어 캡처 N회차 실패"를 명시한다. 절대 헤드리스 그림을 뷰어 그림인 것처럼 보고하지 않는다.

## 4. 반대신문 — 독립 심판

- 프롬프트: **`.claude/loop/judge.md`** (루프 수정 불가, 해시 고정)
- 모델: `fable` · effort `high` — **빌더보다 약하면 안 된다.** 약한 심판은 자기가 못 보는 것을 통과시킨다.
- 모달리티: 빌더는 코드를 본다. 심판은 **코드와 diff 를 보지 않고** 스냅샷 이미지·중계 전문·표적 이미지만 본다.
- 심판은 표적 이미지를 **실제로 열어서** 대조해야 하고, 지적마다 근거 파일 위치와 재현 명령을 써야 한다.

5. 지표만 올리는 하드코딩 — 예: 중계 중복을 문장 셔플로만 회피, 코너 수를 이벤트 강제 발생으로 채우기, xG 를 상수로 클램프
6. 요구 범위 밖 재작성 — 정본 계획서 `docs/match_engine_v1_plan.md` 개정

허용 (디자이너 2026-07-29 승인): `data/*.json` 튜닝, `js/game/*.js` 수정, **새 모듈 추가·구조 변경**.

봉인은 문장이 아니라 해시다. 주행 전 사람이 한 번:
```bash
node .claude/loop/guard.mjs --seal
```

## 6. 정지 — 언제 멈추는가

**(A) 도달** — 둘 다 만족:
- `node sim/realism-lint.mjs --matches 12 --delta-matches 40` 종료코드 0 (네 눈금 전부 100%)
- 심판이 **2회 연속** 통과

**(B) 안전정지** — 아래 중 먼저 오는 것:
- **예산**: 벽시계 7시간
- **정체**: 3회차 연속 종합 개선 < 1%p (눈금이 완전 결정론이라 노이즈가 없어 ε 를 작게 잡는다)
- **회차**: 최대 12회차

(A) 없이 (B) 로 멈추면 실패가 아니라 **정직한 중간 보고**다. 남은 거리를 아침 보고서에 수치로 적는다.

## 7. 회차 절차

1. `node .claude/loop/guard.mjs` — 봉쇄 확인. 실패면 즉시 중단.
2. 직전 회차 심판 지적 + 눈금을 읽고, **가장 낮은 눈금 하나**에 집중한다. 한 회차에 전부 고치려 하지 마라.
3. 구현.
4. `node sim/report.mjs --round <N>` → 산출물. 종료코드 1/2 를 구분해 처리.
5. `node sim/realism-lint.mjs --json` → `.claude/loop/match-realism.log.jsonl` 에 append.
6. 뷰어 브라우저 캡처 1회 (실패 시 "환경 흔들림"으로 기록하고 진행).
7. 심판 소환(`fable`/high, `judge.md`) → 판정 전문을 `runs/round-<N>/verdict.md` 로 보관.
8. `node .claude/loop/guard.mjs --full` — 회귀 확인.
9. **회차 단위로 커밋**한다. 되돌릴 단위가 하룻밤이면 되돌릴 수 없다.

## 9. 알려진 출발점 (첫 회차가 읽을 것)

기준선에서 이미 드러난 것들. 진단은 끝났으니 **다시 조사하지 말고 고치는 데 쓰라.**

- **뷰어에 경기장이 사실상 없다 (최우선).** 피치 캔버스가 483×31 CSS 픽셀(화면의 1.64%, 종횡비 15.6:1)로
  렌더된다. `viewer.html` 의 `#pitchwrap` 이 높이를 못 받는 레이아웃 문제로 보인다. 게다가 BUILDUP 구간에는
  `draw(view, state, { hidePlayers: bu })` 로 선수를 아예 안 그려서, 경기 시간 대부분이 빈 화면이다.
  **표적 이미지와 가장 먼 지점이 여기다.** 눈금 M1~M4 는 이 결함을 못 잡는다 — 시뮬 상태는 정상이기 때문이다.

- **코너가 발생하지 않는다** — 경기당 0.25회(기준 10.2). 골라인 아웃 분류가 코너로 가지 않는 것으로 보인다.
- **xG/슛 = 0.65** — 기준 0.10 의 6.5배. xG 모델이 슛 하나를 반쯤 골로 계산하고 있다. 골 8.67 의 직접 원인일 가능성이 높다.
- **몰림 p95 = 11명** — 실측상 상시가 아니라 **데드볼·골라인 부근에서 붕괴**한다(t=6000 스냅샷에서 18명이 한쪽 박스). 재개 상황의 진형이 없다.
- **진형 상관 r=0.98** — 팀이 공 x 에 강체처럼 붙어 있다. 역할별 지연·독립 움직임이 없다.
- **토큰 누출** — `commentary.json` 에 `#의` 가 쓰였는데 `commentary.js` 의 `fill()` 이 지원하는 마커는
  `#가 #이 #는 #은 #를 #을 #와 #과` 뿐이다. 조사 마커 집합을 넓히거나 템플릿을 고쳐야 한다.
- **분당 43.3줄 · 실플레이 3.5분** — 디자이너 요구는 10분이다(`stance.json` 의 `pace.matchRealSec`).
  시간을 늘리면 밀도는 자동으로 내려가므로 두 문제를 함께 봐야 한다.
- **개입 델타 +0.20** — 카드를 내든 안 내든 결과가 거의 같다. **게임으로서의 형태가 없다는 뜻이고, 가장 큰 표적이다.**
