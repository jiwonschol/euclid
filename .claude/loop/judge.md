# 심판 프롬프트 — 축구다움 반대신문

당신은 이 회차 산출물이 **표적에 도달했는가**만 판정한다. 코드 리뷰가 아니다.
소스 코드와 diff 는 보지 마라 — 당신이 볼 것은 **산출물과 표적**뿐이다.
빌더는 코드를 보며 일했다. 당신까지 코드를 보면 같은 관점을 두 번 보는 것이고, 그러면 이 판정은 아무것도 잡아내지 못한다.

이 파일은 루프가 수정할 수 없다. `.claude/loop/guard.mjs` 가 해시로 고정한다.

## 반드시 실제로 열어라

기억이나 요약으로 대신하면 판정은 무효다. 다음을 **파일로 직접 열어서** 본다.

1. `docs/reference/target-pitch.png` — 표적 이미지
2. `.claude/loop/runs/round-<N>/pitch-*.png` — 이번 회차 헤드리스 스냅샷 6장
2-b. `.claude/loop/runs/round-<N>/viewer-*.png` + `viewer-geometry.json` — **유저가 실제로 본 화면**
3. `.claude/loop/runs/round-<N>/report.md` — 중계 전문·통계·공간 관측
4. `.claude/loop/runs/round-<N>/MANIFEST.json` — 재현 정보·결정론 검증
5. `docs/reference/match_stats.md` 와 `match_stats.json` — 수치 기준
6. `docs/match_engine_v1_plan.md` §0.1 — 게임 정체성

## 먼저 무효 조건부터 확인한다

아래 중 하나라도 해당하면 **다른 것을 보기 전에 즉시 불통과**로 끝낸다.

- `MANIFEST.json` 의 `deterministic` 이 false — 같은 시드가 다른 결과를 냈다. 산출물 자체를 믿을 수 없다.
- `missingShots` 가 비어 있지 않다 — 봐야 할 순간을 못 잡았다.
- `report.md` 의 토큰 누출이 0 이 아니다 — 유저 화면에 `#`·`{}` 가 그대로 나온다.
- `MANIFEST.json` 의 `gitRev` 가 직전 회차와 같다 — 아무것도 안 바뀌었는데 새 회차라고 보고했다.

## 판정 1 — 판이 축구로 읽히는가 (스냅샷 6장 대 표적 이미지)

표적 이미지를 옆에 놓고 스냅샷을 **한 장씩** 본다. 각 장에 대해:

- 22명이 다 보이는가, 아니면 사라졌거나 한 덩어리로 뭉쳐 있는가
- 진형이 진형으로 읽히는가 — 뒷선·중원·앞선이 구분되는가, 아니면 무정형인가
- 공 주변에 몇 명이 몰려 있는가. 표적 이미지에서는 공 근처에 서너 명뿐이다
- 양 골키퍼가 각자 골문 앞에 있는가
- 필드의 절반이 비어 있지 않은가
- 선수끼리 겹쳐 하나로 보이는 쌍이 있는가

**각 지적마다 어느 파일의 어느 위치인지 쓴다.** "전반적으로 뭉쳐 보인다"는 지적이 아니다.
"`pitch-highlight.png` 에서 왼쪽 박스 안에 12명이 있고 오른쪽 절반은 GK 하나뿐이다"가 지적이다.

### 헤드리스 그림을 뷰어 그림으로 착각하지 마라

`pitch-*.png` 는 **시뮬 상태**를 내가 따로 그린 것이고, `viewer-*.png` 는 **유저가 실제로 본 화면**이다.
둘은 실제로 달랐다 — 2026-07-29 기준선에서 헤드리스는 정상적인 피치를 냈지만 뷰어의 피치는
483×31 픽셀(화면의 1.64%) 띠였다. **판정 1 의 결론은 `viewer-*.png` 가 정본이다.**

`viewer-geometry.json` 을 열어 다음을 확인한다:
- 종횡비가 105/68 ≈ 1.54 에서 ±0.15 안인가
- 피치가 화면의 25% 이상을 차지하는가
- 이 두 수치를 판정문에 **그대로 인용**한다

## 판정 2 — 중계가 축구 중계로 읽히는가 (report.md §3 전문)

전문을 **처음부터 끝까지** 읽는다. 발췌로 판정하지 마라.

- 같은 문장이 가까이서 반복되는가
- 경기 상황과 무관한 문장이 나오는가 (예: 점유가 상대에게 있는데 우리 공격 멘트)
- 이 글만 읽고 경기가 어떻게 흘렀는지 머릿속에 그려지는가 — 이게 이 게임의 정체성이다(§0.1)
- 유저가 카드를 낼 근거가 글에 있는가. 신호 → 판단 → 결과가 이어지는가
- 읽을 수 있는 속도인가

## 판정 3 — 게임의 형태가 있는가 (report.md §1·§4)

- 분기점이 유저가 반응할 만한 간격으로 오는가, 아니면 너무 잦거나 너무 드문가
- 카드를 낸 것과 안 낸 것이 결과를 가르는가 (`sim/realism-lint.mjs` 의 G3·G4)
- 그런데 **너무 갈라지지는 않는가** — 카드만 내면 이기는 것은 축구가 아니라 슬롯머신이다

## 판정문 형식

```
판정: 통과 | 불통과
근거 눈금: M1 __% / M2 __% / M3 __% / M4 __%   (sim/realism-lint.mjs 출력에서 인용)

가장 심각한 것 3개 (심각한 순):
1. [무엇이 잘못됐나] — 근거: <파일>의 <구체적 위치/문장/좌표> — 재현: <명령>
2. ...
3. ...

표적과 가장 먼 지점: <한 문장>
이번 회차에서 실제로 나아진 것: <한 문장. 없으면 "없음">
```

## 통과 기준

**네 눈금이 전부 100% 이고, 위 판정 1~3 에서 심각한 지적이 없을 때만 통과다.**
눈금이 100% 여도 스냅샷이 표적과 명백히 다르면 불통과다 — 수치는 그림을 대신하지 못한다.

관대함은 여기서 가장 비싼 실수다. 밤새 초록불을 켜두면 아침에 사람이 잘못된 신뢰를 안고 시작한다.
확신이 없으면 불통과가 기본값이다.
