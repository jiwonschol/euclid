# Claude Code용 마스터 프롬프트

아래 요구사항을 **현재 저장소에 실제로 구현하라.** 너는 이 게임과 축구를 이미 안다고 가정하지 마라. 현대 액션 축구 게임을 흉내 내거나, 22개의 점을 무작위로 움직이는 것으로 축구를 구현했다고 주장하지 마라.

참고 영상: https://www.youtube.com/watch?v=y8KQA6-yD6M&list=PLnImbEgFfZdHpj292TpTWwW7UFYjV0pwe

이 영상은 `Captain Tsubasa IV`식 경기 표현의 참고다. 핵심은 다음 두 층이다.

1. 위쪽/중앙에는 현재 중요한 플레이를 크게 보여 주는 **시네마틱 경기 장면**이 있다.
2. 동시에 전체 선수와 공의 위치를 보여 주는 **전술 필드/레이더**가 있다.

그러나 완성할 게임은 원작을 그대로 복제하는 액션 게임이 아니다. **축구 선수들은 자율적으로 실제 축구 형태를 유지하며 경기하고, 사용자는 감독으로서 하스스톤의 손패처럼 보이는 카드들을 사용해 전술적 선택을 내리는 반실시간 감독 게임**이다.

저작권이 있는 캐릭터 이름, 팀명, 로고, 스프라이트, 음악, 대사, 필살기 명칭, 스토리 텍스트를 복사하지 마라. 메커니즘과 화면 구성의 정신만 참고하고, 모든 임시 콘텐츠는 오리지널 이름과 단순 도형/자체 제작 플레이스홀더로 구성하라.

---

## 0. 작업 방식

먼저 저장소를 조사하라.

- 프레임워크, 언어, 빌드 도구, 테스트 도구, 진입점, 주요 컴포넌트, 현재 경기 구현 파일을 확인한다.
- 기존 코딩 스타일과 폴더 구조를 따른다.
- 이미 존재하는 기능을 이유 없이 삭제하거나 프로젝트를 새로 갈아엎지 않는다.
- 기존 의존성으로 해결 가능한 일을 위해 대형 라이브러리를 추가하지 않는다.
- 조사 후 10~20줄 이내의 짧은 구현 계획을 제시하고 곧바로 구현한다. 계획만 쓰고 멈추지 않는다.
- 구현을 작은 수직 슬라이스로 나누되, 최종적으로 실제 한 경기를 시작하고 끝낼 수 있는 상태까지 진행한다.
- 각 단계 뒤에 타입 검사, 단위 테스트, 빌드 또는 해당 저장소의 검증 명령을 실행한다.
- 막힌 부분이 없다면 중간 승인을 기다리지 말고 계속 진행한다.

React + TypeScript 저장소라면 아래 권장 구조를 사용하되, 현재 저장소가 다른 스택이면 같은 책임 분리를 그 스택에 맞게 적용하라.

```text
src/
  game/
    simulation/       # UI와 분리된 순수 경기 시뮬레이션
    rules/            # 오프사이드, 아웃, 득점, 재개, 반칙
    ai/               # 선수/팀 의사결정과 포지셔닝
    cards/            # 감독 카드, 비용, 효과, 검증
    data/             # 팀, 선수, 포메이션, 카드 데이터
    replay/           # 시드와 명령 로그를 이용한 재현
  ui/
    match/            # 경기 화면, HUD, 카드 손패
    renderers/        # 전술 필드와 시네마틱 표현
  tests/
```

UI가 React라면 22명과 공의 지속적인 이동은 Canvas 또는 SVG로 렌더링하고, 카드·HUD·툴팁은 일반 UI 컴포넌트로 구현하라. 시뮬레이션 코어는 React state와 분리한다.

## 1. 제품의 절대적인 핵심

이 게임은 다음 세 가지가 동시에 성립해야 한다.

### A. 축구 시뮬레이션

- 양 팀 11명, 그중 한 명은 골키퍼다.
- 공은 실제 위치와 속도를 가진 단 하나의 객체다.
- 선수들은 포메이션, 역할, 공 위치, 소유권, 동료와 상대의 위치에 따라 이동한다.
- 공격·수비·공수 전환의 형태가 눈에 보여야 한다.
- 오프사이드, 득점, 스로인, 골킥, 코너킥, 프리킥, 페널티킥, 전후반, 진영 교대가 규칙 엔진에서 처리된다.

### B. Captain Tsubasa식 표현

- 중요한 1대1, 패스, 슛, 공중볼, 골키퍼 선방은 큰 시네마틱 장면으로 강조한다.
- 시네마틱 결과는 애니메이션이 임의로 정하지 않는다. 반드시 시뮬레이션이 먼저 결과를 계산하고, UI는 그 결과를 표현한다.
- 전체 위치는 전술 필드/레이더에서 계속 확인할 수 있다.

### C. 하스스톤식 감독 손패

- 사용자는 선수를 직접 방향키로 조작하지 않는다.
- 선수들은 기본 AI로 정상적인 축구를 계속한다.
- 손패의 카드는 `패스 버튼`, `슛 버튼`의 단순 치환이 아니라 감독의 전술 지시다.
- 카드가 없어도 선수는 패스, 드리블, 슛, 수비를 한다.
- 카드는 행동 확률, 우선순위, 포지셔닝, 압박, 위험 감수, 특정 상황의 선택을 바꾼다.
- 중요한 상황에서는 맥락 카드가 나타나 즉각적인 선택도 가능하다.

**절대로 축구를 턴제 카드게임으로 바꾸지 마라.** 경기는 반실시간으로 흐르고, 카드는 그 흐름에 개입한다.

## 2. 경기 화면

데스크톱 16:9를 우선으로 하되 1280×720에서도 깨지지 않게 한다.

```text
┌──────────────────────────────────────────────────────────┐
│ 팀A  1 - 0  팀B             32:18  /  전반              │  ScoreHeader
├──────────────────────────────────────────────────────────┤
│                                                          │
│             CINEMATIC ACTION STAGE                       │
│   현재 볼 소유자, 압박자, 패스/슛/태클/선방 연출          │
│                                                          │
├──────────────────────────────────────────────────────────┤
│              TACTICAL PITCH / RADAR                      │
│     22명, 공, 포메이션, 소유권, 이동을 정확히 표시        │
├──────────────────────────────────────────────────────────┤
│ 감독 초상/CP   [카드][카드][카드][카드][카드]   활성전술 │  CardHand
└──────────────────────────────────────────────────────────┘
```

필수 UI 구성:

- 상단 중앙: 팀명, 점수, 경기 시계, 전반/후반, 현재 재개 상태.
- 중앙 상단: 시네마틱 액션 스테이지.
- 중앙 하단: 전술 필드. 양 팀 색을 명확히 구분하고 선수 등번호 또는 짧은 식별자를 표시한다.
- 화면 하단: 5장 안팎의 카드가 부채꼴로 겹치는 손패.
- 카드 왼쪽 위: 비용.
- 카드 중앙: 아이콘/일러스트 플레이스홀더.
- 카드 아래: 이름, 짧은 효과, 지속시간 또는 사용 조건.
- 플레이 가능한 카드는 명확히 강조하고, 불가능한 카드는 흐리게 표시하며 마우스를 올리면 정확한 불가 이유를 보여 준다.
- 카드는 클릭 후 목표를 선택하는 방식과 드래그 방식 중 최소 하나를 완성하고, 가능하면 둘 다 지원한다.
- 목표 지정 카드 선택 중에는 유효한 선수/지역만 하이라이트한다.
- 현재 적용 중인 전술은 작은 상태 칩으로 표시하고 남은 시간을 보여 준다.
- 최근 사건 로그를 접을 수 있는 패널로 제공한다. 예: `12:04 오프사이드`, `17:22 슛 차단`, `31:08 높은 압박 시작`.
- 속도 `1x / 2x`와 일시정지 버튼을 둔다. 중요한 선택 창과 시네마틱 동안에는 경기 시계를 멈춘다.

카드가 전술 필드를 완전히 덮어서는 안 된다. 카드에 마우스를 올렸을 때만 위로 크게 올라오게 하라.

## 3. 경기 좌표와 시간

시뮬레이션의 기준 좌표를 명확히 하나로 통일한다.

권장:

```ts
// 실제 축구장 비율에 가까운 월드 좌표
x: -52.5 .. +52.5   // 길이 105m
z: -34.0 .. +34.0   // 폭 68m
ballY: 0 ..          // 공의 높이. 2D 구현이면 별도 height 값
```

- 전반에 Team A는 +x 방향, Team B는 -x 방향으로 공격한다.
- 후반 시작 때 공격 방향과 포메이션 앵커를 정확히 뒤집는다.
- 렌더러 좌표와 시뮬레이션 좌표를 섞지 말고 변환 함수를 둔다.
- 시뮬레이션은 고정 시간 간격으로 진행한다. 권장 10~20Hz.
- 화면은 60fps로 보간 렌더링한다.
- `setInterval` 여러 개로 선수마다 제각각 움직이게 하지 않는다.
- 경기 시간은 45분씩 두 번이지만 실제 플레이 시간은 설정 가능한 압축 배율을 사용한다. 예: 한 경기 12~20분.
- 시네마틱/선택 창에서 시뮬레이션이 멈추면 경기 시계도 멈춘다.
- 모든 난수는 시드 기반 RNG를 사용한다. 같은 시드와 같은 감독 명령 로그로 같은 결과를 재현할 수 있어야 한다.

## 4. 핵심 상태 모델

아래와 동등한 정보를 갖는 명시적인 타입을 만들어라. 이름은 저장소 스타일에 맞게 조정할 수 있지만 책임은 합치지 마라.

```ts
type MatchPhase =
  | 'PRE_KICKOFF'
  | 'KICKOFF'
  | 'IN_PLAY'
  | 'DECISION_WINDOW'
  | 'CINEMATIC_RESOLUTION'
  | 'STOPPAGE'
  | 'HALFTIME'
  | 'FULLTIME'
  | 'PENALTY_SHOOTOUT';

type BallMode =
  | 'CONTROLLED'
  | 'GROUND_PASS'
  | 'AERIAL_PASS'
  | 'SHOT'
  | 'LOOSE'
  | 'OUT_OF_PLAY'
  | 'DEAD_BALL';

interface MatchState {
  phase: MatchPhase;
  half: 1 | 2;
  clockSeconds: number;
  score: Record<TeamId, number>;
  attackDirection: Record<TeamId, 1 | -1>;
  possessionTeamId: TeamId | null;
  restart: RestartState | null;
  players: Record<PlayerId, PlayerState>;
  teams: Record<TeamId, TeamState>;
  ball: BallState;
  pendingEncounter: EncounterState | null;
  activeCardEffects: ActiveCardEffect[];
  offsideSnapshot: OffsideSnapshot | null;
  eventLog: MatchEvent[];
  rngState: SeededRngState;
}

interface PlayerState {
  id: PlayerId;
  teamId: TeamId;
  shirtNumber: number;
  role: 'GK' | 'CB' | 'FB' | 'WB' | 'DM' | 'CM' | 'AM' | 'W' | 'ST';
  position: Vec2;
  velocity: Vec2;
  facing: Vec2;
  homeAnchor: Vec2;
  desiredPosition: Vec2;
  actionState: PlayerActionState;
  stamina: number;       // 장기 체력 0..100
  guts: number;          // 필살기/고강도 행동 자원 0..100 또는 더 큰 정수
  yellowCards: number;
  sentOff: boolean;
  hasBall: boolean;
  markTargetId: PlayerId | null;
  attributes: PlayerAttributes;
  traits: string[];
  cooldowns: Record<string, number>;
}

interface PlayerAttributes {
  pace: number;
  acceleration: number;
  stamina: number;
  strength: number;
  control: number;
  dribble: number;
  shortPass: number;
  longPass: number;
  vision: number;
  finishing: number;
  shotPower: number;
  tackling: number;
  interception: number;
  positioning: number;
  heading: number;
  jumping: number;
  composure: number;
  // GK가 아니면 낮거나 0
  gkPositioning: number;
  gkHandling: number;
  gkReflexes: number;
  gkDiving: number;
  gkOneOnOne: number;
  gkKicking: number;
}

interface BallState {
  position: Vec3;
  velocity: Vec3;
  spin: Vec3;
  mode: BallMode;
  ownerId: PlayerId | null;
  lastTouchPlayerId: PlayerId | null;
  lastTouchTeamId: TeamId | null;
  intendedTargetPlayerId: PlayerId | null;
  intendedTargetPoint: Vec2 | null;
  sourceActionId: string | null;
}
```

불변조건을 코드와 테스트로 지켜라.

- 공 소유자는 최대 한 명이다.
- `ball.ownerId !== null`이면 해당 선수의 `hasBall === true`다.
- 퇴장 선수는 경기장에 존재하지 않는다.
- 한 팀의 활성 선수가 11명을 넘지 않는다.
- 득점은 오직 `GOAL` 규칙 이벤트로만 증가한다.
- 한 번 아웃된 공에는 정확히 한 번의 재개가 생성된다.
- 모든 좌표와 속도는 유한수이며 `NaN`이 없어야 한다.

## 5. 포메이션은 고정 점이 아니라 움직이는 팀 구조다

최소 포메이션:

- 4-3-3
- 4-4-2
- 3-5-2

포메이션 데이터는 팀 기준 정규화 좌표로 정의하고 공격 방향에 맞춰 미러링한다.

예시 4-3-3 앵커:

```ts
const formation433 = {
  GK:  [0.05, 0.50],
  LB:  [0.22, 0.16],
  LCB: [0.18, 0.39],
  RCB: [0.18, 0.61],
  RB:  [0.22, 0.84],
  DM:  [0.40, 0.50],
  LCM: [0.50, 0.34],
  RCM: [0.50, 0.66],
  LW:  [0.70, 0.16],
  ST:  [0.78, 0.50],
  RW:  [0.70, 0.84],
};
```

실제 목표 위치는 다음 요소를 합쳐 계산한다.

```text
desiredPosition =
  formationAnchor
  + ballRelativeShift
  + possessionPhaseShift
  + roleInstructionOffset
  + activeCardModifier
  + markingOrCoverOffset
  + localSeparationCorrection
```

팀 형태의 필수 원칙:

- 공이 왼쪽에 있으면 팀 전체가 왼쪽으로 이동하되 반대편 선수가 완전히 붙지 않고 폭을 유지한다.
- 공격 시 수비수 전원이 공 앞으로 뛰지 않는다. 최소 2명과 골키퍼는 역습 대비 구조를 남긴다.
- 수비 시 10명이 공만 쫓지 않는다.
- 공을 가진 상대에게 가장 가까운 한 명이 `first defender`가 되어 압박 또는 지연한다.
- 두 번째 수비자는 뒤와 안쪽을 커버한다.
- 나머지는 패스 길, 중앙, 위험 선수를 맡으며 라인을 유지한다.
- 기본 최대 적극 압박 인원은 2명, 높은 압박 전술에서도 3명을 넘지 않게 한다.
- 센터백 한 명이 전진하면 다른 센터백은 반드시 커버한다.
- 수비형 미드필더는 중앙과 페널티 박스 앞 공간을 보호한다.
- 풀백/윙백은 공격 시 폭과 오버래핑을 제공하지만 반대쪽 수비 구조와 체력을 고려한다.
- 윙어는 폭을 만들거나 안쪽으로 침투하고, 스트라이커는 센터백을 묶고 오프사이드 라인을 보며 침투한다.
- 선수끼리 겹치지 않도록 분리 힘을 적용하되, 포메이션과 역할보다 강하지 않게 한다.

팀의 경기 국면을 매 틱 분류한다.

```ts
type TeamPhase =
  | 'ORGANIZED_ATTACK'
  | 'ATTACKING_TRANSITION'
  | 'ORGANIZED_DEFENSE'
  | 'DEFENSIVE_TRANSITION'
  | 'SET_PIECE_FOR'
  | 'SET_PIECE_AGAINST';
```

공을 빼앗은 직후 3~5초는 공격 전환, 공을 잃은 직후 3~5초는 수비 전환이다. 카드와 팀 성향에 따라 빠른 역습, 짧은 카운터프레스, 즉시 복귀 중 하나를 선택한다.

## 6. 선수 행동 AI

머신러닝이 필요하지 않다. **규칙 기반 역할 할당 + utility scoring**을 사용하라.

매 의사결정 주기마다:

1. 현재 가능한 합법적 행동을 만든다.
2. 각 행동의 기대 효용을 계산한다.
3. 팀 전술, 선수 성향, 감독 카드 효과를 반영한다.
4. 시드 기반의 작은 노이즈를 넣는다.
5. 가장 높은 행동을 선택한다.

공격 행동 후보:

- 전진 드리블
- 안전한 드리블/볼 보호
- 짧은 패스
- 전진 패스
- 측면 전환
- 스루패스
- 크로스
- 원투패스
- 슛
- 공을 뒤로 돌림

예시 효용 개념:

```text
passUtility =
  passCompletionProbability * progressionValue
  + chanceCreationValue
  + tacticalBias
  - turnoverDanger
  - offsideRisk

shotUtility =
  estimatedGoalProbability * goalValue
  - blockRisk
  - badAnglePenalty
  - staminaOrGutsCost

 dribbleUtility =
  beatDefenderProbability * spaceGain
  + tacticalBias
  - turnoverRisk
```

반드시 지켜야 할 행동 상식:

- 자기 진영 깊은 곳에서 압박받는 센터백은 낮은 성공률의 중앙 드리블보다 안전한 패스/클리어를 선호한다.
- 공격수는 동료가 패스할 때까지 오프사이드 라인보다 약간 뒤에서 침투 타이밍을 기다린다.
- 패스 받을 선수는 가만히 서 있지 않고 패스 길과 빈 공간을 만든다.
- 공 소유자 주변에 최소 두 개의 다른 패스 각도가 생기도록 지원 삼각형을 만든다.
- 슛은 거리, 각도, 압박, 수비 블록, 골키퍼 위치를 고려한다.
- 아무 선수나 중앙선에서 반복 슛하지 않는다.
- 전술이 `패스 중심`이면 패스 효용을 높이고, `개인기 중심`이면 드리블 효용을 높이되 합법성과 물리 조건은 그대로 유지한다.

수비 행동 후보:

- jockey/지연
- 태클
- 패스 길 차단
- 슛 블록
- 특정 선수 마크
- 커버
- 수비 라인 복귀
- 공중볼 경합
- 클리어

수비수는 공과 자기 골문 사이를 우선 보호한다. 무조건 공의 현재 좌표로 직선 돌진하지 않는다.

## 7. 공과 패스, 슛, 공중볼

공은 순간이동하지 않는다.

### 패스

- 패스는 `targetPlayer`가 아니라 우선 `targetPoint`와 초기 속도를 가진다.
- 움직이는 동료에게는 현재 위치가 아니라 예측 위치로 리드 패스를 한다.
- 지상 패스는 마찰로 감속한다.
- 로빙 패스와 크로스는 높이, 중력, 착지 시간과 착지점을 가진다.
- 공 궤적의 일정 폭 안에 있는 수비수는 자신의 반응 시간과 이동 속도를 고려해 가로채기를 시도한다.
- 패스가 너무 세거나 약하면 수신자의 퍼스트 터치가 불리해진다.
- 빈 공간 패스는 가장 가까운 선수에게 공을 순간 배정하지 말고, 실제로 공과 선수들이 그 지점으로 달리게 한다.

### 볼 컨트롤

- 선수가 공에 가까워도 공 속도가 너무 높으면 즉시 소유하지 못한다.
- `control`, 압박, 공 높이, 몸 방향, 피로에 따라 깔끔한 컨트롤/긴 터치/실패를 결정한다.
- 소유권이 확정되지 않은 공은 `LOOSE` 상태다.

### 슛

슛은 다음을 고려한다.

- 골문까지 거리
- 보이는 골문 각도
- 슈팅 발과 몸 방향
- 압박 강도
- 수비수의 블록 경로
- 슈팅 능력, 파워, 침착성
- 골키퍼의 위치와 시야
- 공의 높이와 첫 터치 여부
- 일반 슛인지 특수 기술인지

슛 결과를 단일 랜덤 확률로만 처리하지 말고 최소 다음 순서로 나눈다.

1. 정확도: 공이 골문 안으로 향하는가.
2. 블록: 수비수가 궤도에 들어오는가.
3. 골키퍼 도달: 반응 시간과 도달 범위가 충분한가.
4. 처리: 캐치, 펀치, 패리, 실점 중 무엇인가.

### 공중볼

- 공중볼에는 착지점과 도착 시간이 있다.
- 주변 선수는 `heading`, `jumping`, `positioning`, `strength`, 피로로 경합한다.
- 헤더, 발리, 트랩, 클리어, 흘리기를 상황에 따라 선택한다.
- 높은 공과 낮은 공을 구분하면 특수 기술 조건과 연출에 활용할 수 있다.

## 8. Captain Tsubasa식 대결과 시네마틱 상태 머신

중요한 접촉에서만 대결 이벤트를 만든다. 모든 사소한 패스마다 긴 컷신을 재생하지 않는다.

```ts
type EncounterType =
  | 'BALL_CARRIER_DUEL'
  | 'PASS_INTERCEPTION'
  | 'SHOT_BLOCK'
  | 'AERIAL_DUEL'
  | 'GOALKEEPER_SAVE'
  | 'GOALKEEPER_ONE_ON_ONE'
  | 'SPECIAL_MOVE';
```

처리 순서:

1. 시뮬레이션이 대결 조건을 감지한다.
2. 현재 상태를 스냅샷하고 `EncounterStarted` 이벤트를 생성한다.
3. 공격 AI와 수비 AI의 기본 선택을 정한다.
4. 사용자에게 유효한 맥락 카드가 있으면 짧은 선택 창을 연다.
5. 선택이 끝나거나 시간이 지나면 순수 resolver가 결과를 계산한다.
6. `EncounterResolved` 이벤트에 성공/부분 성공/루즈볼/반칙/실패 결과를 기록한다.
7. UI는 그 결과에 맞는 시네마틱을 재생한다.
8. 애니메이션 종료 후 이미 계산된 결과를 경기 상태에 적용하고 재개한다.

공격-수비 대응 관계:

- 드리블 ↔ 태클/지연
- 패스 ↔ 패스 차단
- 슛 ↔ 블록
- 원투 ↔ 압박/패스 길 차단
- 공중 슛/트랩 ↔ 경합/클리어
- 골키퍼 1대1: 드리블/슛/칩 ↔ 돌진/자세 유지

잘못된 대응을 골랐다고 무조건 100% 실패시키지 말라. 통계와 상황에 큰 보정만 준다.

권장 대결 점수:

```text
attackScore =
  관련 공격 능력치
  + 체력/거츠 보정
  + 지원 인원/공간 보정
  + 기술 보정
  + 카드 보정
  + 작은 시드 난수

defenseScore =
  관련 수비 능력치
  + 위치/각도 보정
  + 커버 인원 보정
  + 기술 보정
  + 카드 보정
  + 작은 시드 난수
```

점수 차이가 크면 깔끔한 성공/실패, 근소하면 공이 튀거나 자세가 무너지는 부분 결과를 만든다. 모든 계수는 한 설정 파일에 모아 튜닝 가능하게 한다.

## 9. 골키퍼는 특수 포지션이다

골키퍼를 일반 필드 플레이어 AI에 `role: GK`만 붙여 처리하지 마라. 전용 의사결정과 상태를 둔다.

필수 행동:

- 골문과 공을 잇는 각도를 줄이는 기본 위치 선정
- 슛에 대비한 set position
- 낮은/높은 슛 다이빙
- 캐치
- 펀치/패리
- 크로스에 뛰어나오기 또는 골문에 남기
- 스루패스 스위핑
- 1대1 돌진 또는 자세 유지
- 잡은 뒤 짧은 배급/긴 킥
- 페널티 박스 밖에서는 발로만 플레이

골키퍼 위치 원칙:

- 공이 멀면 골라인에 붙어 있지 않고 수비 라인 뒤 공간을 일부 커버한다.
- 공이 측면으로 가면 가까운 포스트와 골문 중앙 사이에서 각도를 맞춘다.
- 공이 박스 안 중앙으로 들어오면 슈터와 골문 사이를 좁힌다.
- 돌진은 각도를 줄이지만 칩/드리블에 취약하다.
- 크로스에 무조건 뛰어나오지 않는다. 도착 시간, 혼잡도, 처리 성공률을 비교한다.

선방 계산 요소:

- 슛 속도와 거리에서 나오는 반응 가능 시간
- 슛의 목표 지점과 골키퍼의 현재 위치
- `gkPositioning`, `gkReflexes`, `gkDiving`, `gkHandling`
- 수비수/공격수가 시야를 가렸는지
- 골키퍼가 미리 set 상태인지, 이동 중인지
- 피로와 특수 선방 기술

캐치는 성공하면 소유권을 확정한다. 펀치/패리는 성공률이 더 높을 수 있지만 공을 `LOOSE`로 만들고 세컨드 볼 위험을 남긴다.

규칙:

- 골키퍼의 손 사용 가능 여부는 **공의 위치가 자기 페널티 박스 안인지**로 판정한다.
- 자기 팀 선수가 발로 의도적으로 골키퍼에게 준 백패스나 같은 팀 스로인을 직접 받은 경우 손으로 잡을 수 없다.
- 손으로 잡은 공을 놓은 뒤 다른 선수가 건드리기 전에 다시 손으로 잡지 않는다.
- MVP에서는 골키퍼의 시간 지연 세부 규칙은 생략할 수 있지만 상태가 영원히 멈추지 않게 배급 타이머를 둔다.

## 10. 오프사이드: 반드시 패스 순간의 스냅샷으로 판정

오프사이드는 `공을 받을 때 공격수가 수비수보다 앞에 있으면 반칙`이라는 단순 규칙이 아니다.

공격 방향 기준으로, 같은 팀 동료가 공을 의도적으로 플레이한 순간 다음 조건을 모두 만족하면 그 선수는 오프사이드 **위치 후보**다.

1. 상대 진영에 있다. 중앙선 위 또는 자기 진영이면 아니다.
2. 공보다 상대 골라인에 가깝다.
3. 두 번째로 골라인에 가까운 상대 선수보다 상대 골라인에 가깝다.

여기서 `두 번째 상대 선수`는 흔히 골키퍼와 마지막 수비수지만, 골키퍼가 앞으로 나온 경우 골키퍼라고 가정하면 안 된다. 모든 상대의 공격 방향 좌표를 정렬해 두 번째 선수를 사용하라.

판정 절차:

```ts
interface OffsideSnapshot {
  createdAt: number;
  attackingTeamId: TeamId;
  sourcePlayerId: PlayerId;
  sourceTouchPosition: Vec2;
  ballLine: number;
  secondLastOpponentLine: number;
  candidatePlayerIds: PlayerId[];
  exemptRestart: boolean;
}
```

- 동료가 패스/슛/의도적 터치를 하는 바로 그 순간 스냅샷을 만든다.
- 단순히 후보 위치에 있었다는 이유로 즉시 휘슬을 불지 않는다.
- 후보가 공을 터치하거나, 공을 두고 상대와 경합하거나, 상대의 플레이 또는 골키퍼 시야를 명백히 방해하거나, 골대/골키퍼/수비수의 세이브성 굴절에서 이득을 얻을 때 오프사이드 반칙을 선언한다.
- 후보가 플레이에 관여하지 않으면 경기를 계속한다.
- 상대가 공을 의도적으로 새로 플레이하면 후보 상태를 해제한다. 단, 단순 굴절이나 골키퍼/수비수의 deliberate save는 해제하지 않는다.
- 새 동료 터치가 발생하면 새 스냅샷으로 교체한다.
- 스로인, 골킥, 코너킥을 직접 받은 상황에는 오프사이드를 적용하지 않는다.
- 프리킥에는 일반 오프사이드가 적용된다.

2D 마커의 중심만 비교해 화면상 억울한 판정이 나지 않도록 선수 반지름 또는 공격 방향으로 가장 앞선 신체 지점을 일관되게 사용하고 0.1~0.2m 정도의 수치 허용오차를 둔다.

공격 AI도 오프사이드를 이해해야 한다.

- 기본적으로 두 번째 수비수 라인보다 0.5~1.0m 뒤에 머문다.
- 패서가 킥 동작에 들어가면 침투 타이밍을 잡는다.
- 패스 터치가 발생한 뒤에는 수비 라인 뒤로 달려도 된다.
- `오프사이드 트랩` 카드가 활성화되면 수비 라인이 함께 전진하지만, 한 명만 남으면 함정이 깨질 수 있다.

오프사이드 테스트를 반드시 작성한다.

1. 상대 진영에서 공과 두 번째 수비수보다 앞선 공격수가 패스를 받아 터치 → 오프사이드.
2. 수비수보다 앞이지만 공보다 뒤 → 온사이드.
3. 자기 진영 → 온사이드.
4. 스로인/골킥/코너 직접 수령 → 온사이드.
5. 오프사이드 위치 선수가 관여하지 않고 다른 온사이드 선수가 플레이 → 계속.
6. 상대의 의도적 플레이 뒤 수령 → 계속.
7. 골키퍼 선방에서 튄 공을 기존 후보가 플레이 → 오프사이드.

## 11. 득점, 아웃, 재개와 반칙

### 득점

- 공 전체가 골포스트 사이, 크로스바 아래의 골라인을 완전히 통과해야 득점이다.
- 직전 공격 과정에 오프사이드나 반칙이 확정되어 있으면 득점을 취소한다.
- 득점 후 상대 팀의 중앙 킥오프로 재개한다.

### 터치라인 아웃

- 공 전체가 터치라인을 넘으면 마지막으로 건드리지 않은 팀의 스로인.
- 재개 위치는 공이 나간 지점 근처.
- MVP에서 실제 팔 동작은 단순화해도 되지만 직접 수령에는 오프사이드가 없다는 규칙은 지킨다.

### 골라인 아웃

득점이 아닌 상태로 공 전체가 골라인을 넘었을 때:

- 마지막 터치가 공격 팀이면 수비 팀 골킥.
- 마지막 터치가 수비 팀이면 공격 팀 코너킥.

### 킥오프

- 득점 후 실점 팀이 중앙에서 재개한다.
- 전후반 시작 시 킥하는 선수 외 모든 선수는 자기 진영에 있고, 상대는 공에서 9.15m 이상 떨어진다.
- 공은 센터 마크에 정지해 있어야 하며 명확히 움직이면 인플레이가 된다.

### 프리킥과 페널티킥

태클 resolver가 접촉의 시간, 방향, 공 터치 여부, 강도를 평가해 다음 중 하나를 낸다.

- 합법적 태클
- careless foul: 직접 프리킥
- reckless foul: 직접 프리킥 + 옐로카드
- excessive force/명백한 폭력: 직접 프리킥 + 레드카드

수비 팀이 자기 페널티 박스 안에서 직접 프리킥 대상 반칙을 하면 페널티킥이다. 일반 프리킥에서 상대 선수는 특별한 예외가 없는 한 공에서 9.15m 이상 떨어지도록 재배치한다. 페널티킥에서는 키커와 수비 골키퍼 외 선수들이 페널티 박스 밖, 페널티 마크 뒤, 공에서 9.15m 이상 떨어진 위치에 있도록 한다.

필드 플레이어의 고의 핸드볼은 팔/손 충돌을 실제로 모델링할 때만 구현한다. MVP에서 손/팔 물리가 없다면 무작위 핸드볼을 만들지 말고 비지원 규칙으로 명시한다.

MVP에서는 어드밴티지 규칙을 생략하고 즉시 정지해도 된다. 다만 확장 가능하도록 `FoulEvent`를 독립 이벤트로 만든다.

### 카드와 퇴장

- 옐로카드 2장은 레드카드와 동일하게 퇴장.
- 퇴장 선수를 즉시 활성 선수 집합에서 제거한다.
- 남은 선수들은 현재 포메이션을 축소 재배치한다.
- 퇴장 팀이 계속 11명처럼 움직이면 안 된다.

### 전후반과 교체

- 전반 45분, 후반 45분.
- 하프타임에 진영을 바꾸고 선수 체력/거츠를 일부 회복한다.
- 교체 수, 최소 경기 인원, 연장/승부차기 여부는 `CompetitionRules` 설정으로 둔다.
- 기본값은 현대 규칙형 5명 교체로 두되, 클래식 모드에서 3명으로 바꿀 수 있게 한다. 활성 선수가 7명 미만이 되는 비정상 상황은 경기 중단 상태로 처리할 수 있게 한다.
- 녹아웃 경기 설정에서만 동점 후 연장/승부차기를 사용한다.

## 12. 감독 카드 시스템: 하이브리드 방식

순수 랜덤 손패 때문에 기본 축구 행동을 못 하는 상황을 만들지 마라. 다음 하이브리드를 사용한다.

### 손패 구성

- 일반 전술 덱에서 뽑은 카드 3~5장.
- 큰 상황이 생길 때 임시로 나타나는 맥락 카드 1~2장.
- 맥락 카드는 덱에서 뽑지 않으며 상황이 끝나면 사라진다.
- 손패 최대치는 6 또는 7.
- 오래도록 사용할 수 없는 카드만 손에 남는 현상을 막기 위해 일정 시간 이상 비활성인 카드는 교환 가능하게 한다.

### 자원

`Command Points(CP)`를 사용한다.

- 최대 10.
- 시작 3.
- 일정 경기 시간마다 회복.
- 공을 되찾거나 좋은 플레이가 성공했을 때 소량 보너스 가능.
- 중요한 선택 창에서 기본 맥락 카드 일부는 0~1 비용.
- 자원 수치는 HUD에 항상 보인다.

### 카드 타입

```ts
type CardTiming =
  | 'ANYTIME'
  | 'IN_POSSESSION'
  | 'OUT_OF_POSSESSION'
  | 'ATTACKING_TRANSITION'
  | 'DEFENSIVE_TRANSITION'
  | 'FINAL_THIRD'
  | 'GOALKEEPER_DUEL'
  | 'SET_PIECE'
  | 'STOPPAGE';

type CardTargetType =
  | 'NONE'
  | 'OWN_PLAYER'
  | 'OPPONENT_PLAYER'
  | 'PITCH_ZONE'
  | 'BALL_CARRIER'
  | 'FORMATION_ROLE';

interface CoachCard {
  id: string;
  name: string;
  category: 'MENTALITY' | 'PRESS' | 'BUILDUP' | 'ATTACK' | 'DEFENSE' | 'PLAYER' | 'KEEPER' | 'SET_PIECE';
  cost: number;
  timing: CardTiming[];
  targetType: CardTargetType;
  durationMatchSeconds: number | null;
  cooldownGroup: string | null;
  preconditions: CardCondition[];
  effects: TacticalModifier[];
  rulesText: string;
  tradeoffText: string;
}
```

효과는 데이터 기반 modifier로 적용한다.

```ts
interface TacticalModifier {
  key: string;
  scope: 'TEAM' | 'ROLE' | 'PLAYER' | 'ZONE' | 'NEXT_ACTION';
  targetId?: string;
  operation: 'ADD' | 'MULTIPLY' | 'OVERRIDE';
  value: number | string | boolean;
  stacking: 'REPLACE' | 'REFRESH' | 'STACK' | 'REJECT';
}
```

UI 컴포넌트 안에 카드별 `if` 문을 흩뿌리지 않는다. 카드 validator와 effect system을 독립시킨다.

### 기본 카드 예시

아래 카드 중 최소 12장을 데이터로 구현한다. 이름은 프로젝트 분위기에 맞춰 오리지널로 바꿔도 된다.

1. **높은 압박** / 비용 3 / 20초  
   압박선과 라인을 올리고 최대 압박 인원을 늘린다. 공 탈취 확률과 피로 소모가 증가하며 뒷공간 위험도 커진다.

2. **낮은 블록** / 비용 2 / 20초  
   수비 라인과 팀 높이를 낮추고 중앙 간격을 좁힌다. 스루패스에 강하지만 상대에게 중거리 슛과 점유를 허용한다.

3. **즉시 복귀** / 비용 1 / 수비 전환  
   카운터프레스를 포기하고 전원이 수비 형태로 복귀한다.

4. **카운터프레스** / 비용 2 / 수비 전환  
   공을 잃은 주변 2~3명이 짧게 압박한다. 성공하면 높은 위치에서 되찾지만 실패하면 구조가 열린다.

5. **왼쪽 오버랩** / 비용 1 / 12초  
   왼쪽 풀백/윙백이 전진하고 왼쪽 윙어는 안쪽으로 이동한다. 반대편 수비수가 균형을 잡는다.

6. **오른쪽 오버랩** / 비용 1 / 12초  
   위 카드의 반대쪽.

7. **측면 전환** / 비용 1 / 다음 소유 행동  
   공 반대쪽의 빈 공간을 탐색하고 장거리 대각 패스 효용을 높인다.

8. **침투 패스** / 비용 2 / 공격 진영  
   온사이드 침투자가 있고 패스 길이 있을 때 다음 행동에서 스루패스 효용을 크게 높인다. 유효한 침투자가 없으면 사용 불가다.

9. **빠른 크로스** / 비용 1 / 측면 공격  
   공을 오래 끌기보다 이른 크로스를 우선한다. 박스 안 인원이 부족하면 사용 불가 또는 효과가 약하다.

10. **패스워크 중심** / 비용 2 / 25초  
    짧은 패스, 원투, 지원 삼각형을 우선하고 드리블 위험을 낮춘다.

11. **개인기 중심** / 비용 2 / 20초  
    뛰어난 드리블러의 1대1 시도 가중치를 높인다. 턴오버 위험과 거츠 소모가 증가한다.

12. **템포 낮추기** / 비용 1 / 25초  
    안전 패스, 볼 유지, 체력 보존을 우선한다.

13. **전원 공격** / 비용 5 / 30초  
    라인과 박스 침투 인원을 크게 올린다. 반드시 최소한의 역습 대비만 남고 수비 위험이 크게 증가한다.

14. **핵심 선수 밀착 마크** / 비용 2 / 상대 선수 대상  
    가장 적합한 수비수 한 명이 지정 상대를 추적한다. 한 수비수가 여러 명을 동시에 마크할 수 없다.

15. **중거리 슛 허용** / 비용 2 / 15초  
    일정 능력 이상 선수의 슛 임계값을 낮춘다. 무리한 슛 증가라는 단점이 있다.

16. **거츠 절약** / 비용 1 / 30초  
    특수 기술 사용 임계값을 높이고 일반 행동을 우선한다.

### 맥락 카드 예시

- 볼 소유 대결: `드리블 강행`, `안전 패스`, `원투`, `즉시 슛`.
- 수비 대결: `태클`, `패스 길 차단`, `슛 블록`, `지연`.
- 골키퍼 1대1: `돌진`, `자세 유지`.
- 슛 대응: `캐치 시도`, `펀치/패리`.
- 코너킥: `니어 포스트`, `파 포스트`, `짧은 코너`.
- 프리킥 수비: `벽 왼쪽`, `벽 오른쪽`, `골키퍼 중심 유지`.

맥락 카드는 현재 행동 resolver에 보정을 주지만, 공 위치와 선수 능력을 무시하고 결과를 강제로 만들지 않는다.

### 카드 검증 순서

1. 현재 경기 phase와 timing이 맞는가.
2. CP가 충분한가.
3. 목표가 존재하고 합법적인가.
4. 카드의 전제조건이 참인가.
5. 같은 cooldown group 또는 상호배타 전술과 충돌하지 않는가.
6. 효과 적용 후에만 CP를 차감하고 카드를 버린다.

실패한 카드 플레이는 자원을 소비하지 않는다. 정확한 실패 사유를 UI에 표시한다.

## 13. 거츠와 오리지널 특수 기술

Captain Tsubasa식 과장된 연출을 살리되 IP를 복사하지 않는다.

- 각 선수에게 `guts` 자원을 둔다.
- 고강도 드리블, 특수 패스, 특수 슛, 특수 태클, 특수 선방은 거츠를 소비한다.
- 거츠가 부족하면 해당 기술을 사용할 수 없다.
- 걷거나 플레이에서 멀리 떨어져 있을 때 천천히 회복하고 하프타임에 일부 회복한다.
- 거츠가 매우 낮으면 일반 능력에도 약한 피로 페널티가 생긴다.
- 감독 카드 `적극 플레이`는 특수 기술 사용 임계값을 낮추고, `거츠 절약`은 높인다.

```ts
interface SpecialMove {
  id: string;
  name: string;                    // 오리지널 이름
  type: 'SHOT' | 'DRIBBLE' | 'PASS' | 'TACKLE' | 'BLOCK' | 'SAVE';
  requiredContexts: string[];
  gutsCost: number;
  powerModifier: number;
  accuracyModifier: number;
  successModifier: number;
  animationKey: string;
  tags: string[];
}
```

기술은 상황 조건을 지켜야 한다. 예를 들어 공중 발리 기술은 지상 드리블 중 사용할 수 없고, 특수 선방은 골키퍼만 사용할 수 있다. 강력한 기술도 자동 득점/자동 선방이 아니다.

## 14. 상대 감독과 난이도

상대도 같은 규칙과 같은 시뮬레이션을 사용한다.

- 상대는 점수, 남은 시간, 체력, 공 소유권에 따라 전술을 바꾼다.
- 지고 있고 시간이 적으면 라인을 올리고 위험을 감수한다.
- 이기고 있으면 템포를 낮추고 구조를 안정시킨다.
- 특정 핵심 선수에게 마크를 붙일 수 있다.
- 상대 AI는 사용자가 방금 고른 숨겨진 선택을 미리 읽지 않는다.
- 난이도는 의사결정 노이즈, 반응 시간, 전술 전환 능력으로 조절한다. 단순 스탯 사기나 결과 조작만으로 올리지 않는다.

## 15. 디버그 도구

키 하나로 켜고 끌 수 있는 디버그 오버레이를 만든다. 예: `D`.

표시 항목:

- 선수의 현재 역할과 action state
- home anchor와 desired position
- first defender / cover defender / balance defender
- 패스 목표점과 예상 궤적
- 공의 속도와 mode
- 양 팀 수비 라인
- 오프사이드 라인과 현재 후보
- 활성 카드 modifier와 남은 시간
- 현재 팀 국면
- 골키퍼의 set/rush/claim 상태

또한 다음 개발 기능을 제공한다.

- 고정 시드로 새 경기 시작
- 경기 이벤트 로그 내보내기
- 시드 + 카드 명령 로그로 리플레이
- 10배속 자동 시뮬레이션
- 100경기 일괄 시뮬레이션 결과 요약

디버그 기능은 개발 모드에만 노출해도 된다.

- 11명 중 한 명이 GK인지 검증.
- 후반 시작 시 공격 방향과 포메이션이 정확히 뒤집힘.
- 공 전체가 골라인을 넘었을 때만 득점.
- 마지막 터치 팀에 따라 스로인/골킥/코너가 정확히 선택됨.
- 박스 안 수비 반칙이 페널티킥이 됨.
- 옐로 2장 또는 레드 후 선수가 제거됨.
- 골키퍼가 박스 밖에서 손을 쓰지 못함.
- 의도적 백패스를 손으로 잡지 못함.
- 위에 제시한 오프사이드 7개 사례.

### AI/형태 테스트

- 기본 수비에서 한 팀 10명이 공 주위로 몰리지 않음.
- 기본 최대 적극 압박자가 2명 이하임.
- 높은 압박 카드 동안만 설정 범위 내에서 3명까지 증가함.
- 공격 시 최소 2명+GK가 공 뒤 역습 대비 구조를 유지함.
- 스트라이커가 패스 전 반복적으로 오프사이드 위치에 정지하지 않음.
- 공과 반대편 팀 폭이 완전히 붕괴하지 않음.
- 골키퍼가 일반 공격 상황에서 중앙선까지 떠돌지 않음.

### 카드 테스트

- CP 부족 시 플레이 불가, CP 미차감.
- 잘못된 phase/target이면 불가 사유 표시.
- 카드 효과가 지정 시간 후 종료.
- `REPLACE` 전술은 이전 같은 그룹 효과를 교체.
- `REFRESH`는 중복 수치 증가 없이 시간만 갱신.
- `침투 패스`는 온사이드 침투자와 패스 길이 없으면 비활성.
- 카드 효과가 실제 AI 가중치/포지셔닝에 반영됨.

### 안정성 테스트

- 같은 시드와 같은 카드 로그로 이벤트와 최종 점수가 동일.
- 자동 100경기에서 예외, `NaN`, 무한 정지, 공의 영구 소실이 없음.
- 인플레이인데 공이 30 경기초 이상 움직이지 않는 deadlock이 없음.
- 득점 후 반드시 킥오프로 복귀.
- 한 아웃 상황에서 중복 재개가 생성되지 않음.

### UI 완료 조건

- 1280×720과 1920×1080에서 레이아웃이 겹치거나 잘리지 않음.
- 카드 hover/선택/취소/목표 지정이 작동.
- 무효 카드는 이유가 보임.
- 시네마틱과 레이더가 같은 사건 결과를 보여 줌.
- 브라우저 콘솔 에러 없음.
- 빌드와 타입 검사가 통과.

## 18. 금지 사항

다음 중 하나라도 남아 있으면 완료라고 하지 마라.

- 22명이 공 좌표만 향해 몰려다님.
- 골키퍼가 일반 수비수처럼 필드를 배회함.
- 패스가 순간이동함.
- 오프사이드를 `x > 어떤 값` 하나로 판정함.
- 수비수보다 앞에 있다는 이유만으로 공 터치 전에 즉시 오프사이드 처리함.
- 카드가 합법성, 공 위치, 체력, 오프사이드를 무시하고 성공을 강제함.
- `패스 카드`를 뽑지 못해 선수가 패스를 못 함.
- UI 애니메이션과 실제 시뮬레이션 결과가 다름.
- 카드마다 컴포넌트에 하드코딩된 거대한 조건문이 있음.
- 프레임 속도에 따라 경기 결과가 바뀜.
- 테스트 없이 “그럴듯하게 보인다”는 이유로 완료 처리함.
- 저작권 캐릭터/팀/이미지/음악을 저장소에 복사함.
- 핵심 기능에 TODO, 빈 함수, 가짜 확률 결과가 남음.

# 구현 후 Claude Code에 다시 붙여넣을 검증·수정 프롬프트

현재 구현을 칭찬하거나 설명하는 데 시간을 쓰지 말고, 아래 기준으로 실제 코드를 감사하고 즉시 고쳐라.

1. 시뮬레이션이 UI와 분리된 고정 timestep/시드 기반 구조인지 확인한다.
2. 22명이 공을 쫓는 군집 행동, 패스 순간이동, 골키퍼 배회, 프레임 의존 난수가 있는지 찾는다.
3. 오프사이드가 동료의 터치 순간 스냅샷, 두 번째 상대 선수, 공의 위치, 상대 진영, 실제 관여, 스로인/골킥/코너 예외를 모두 처리하는지 테스트로 증명한다.
4. 공격 시 지원 삼각형과 역습 대비, 수비 시 first defender/cover/balance가 실제로 작동하는지 디버그 오버레이와 테스트로 확인한다.
5. 골키퍼가 전용 상태/의사결정, 박스 안 손 사용, 백패스, 캐치/펀치/패리, 1대1을 갖는지 확인한다.
6. 카드가 단순 UI 장식이 아니라 AI utility, 포지션, 압박, 위험 감수에 실제 modifier를 적용하는지 확인한다.
7. 카드가 기본 축구 행동을 잠그거나 불법 행동/자동 득점을 강제하지 않는지 확인한다.
8. 시네마틱 결과가 시뮬레이션에서 먼저 계산되고 레이더와 일치하는지 확인한다.
9. 같은 시드와 같은 카드 로그로 결과가 재현되는지 확인한다.
10. 100경기 자동 시뮬레이션을 실행해 예외, NaN, deadlock, 중복 재개를 찾고 수정한다.
11. 1280×720에서 카드 손패, 전술 필드, 점수판이 겹치지 않는지 브라우저로 확인한다.
12. 타입 검사, 테스트, 빌드를 모두 실행한다.

문제를 발견하면 보고만 하지 말고 코드를 수정하고 테스트를 추가하라. 마지막에 변경 파일, 수정한 결함, 실행한 명령과 실제 결과를 간결하게 보고하라.
