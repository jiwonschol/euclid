# 그라운드의 유클리드 — 게임 프로토타입 계획서 v0.1

> **이 문서의 성격**: 디자이너(작가)의 머릿속에 있는 프로토타입을 **동작하는 형태**로 옮기기 위한 명세다.
> 이 게임이 실제로 재미있을지는 디자이너 본인도 모른다. 그것을 확인하는 것이 이 프로토타입의 유일한 목적이다.
> 따라서 **완성도보다 동작이, 그래픽보다 반응이 우선한다.** 예쁘게 만들려고 시간을 쓰지 마라.
> 구현 중 이 문서와 충돌하는 판단이 필요하면, 임의로 결정하지 말고 질문하라.

---

## 0. 한 줄 정의

소설 『그라운드의 유클리드』 세계에 들어간 유저가 K리그 팀의 **새 감독**이 되어,
흘러가는 경기를 지켜보다가 **제한된 개입권**으로 흐름을 바꾸는 관전형 전술 게임.
(장르 좌표: 올드 캡틴츠바사 3·4의 커맨드 리듬 × FM의 관전 구조 — 단, FM의 반대 방향. 매니지먼트는 게임이 대신하고, 유저에게는 벤치의 순간만 남긴다.)

## 1. 재미 가설 (이 프로토타입이 검증할 것)

1. **개입 타이밍의 긴장** — "지금 카드를 쓸까, 아낄까"를 고민하는 순간 자체가 재미인가.
2. **따를까, 거스를까** — 참모의 신호(표정/힌트)를 읽고 따르거나 거스르는 선택이 재미인가.
3. **납득되는 패배** — 열세에서 올바른 대처를 못 하면 쳐맞는 경기가, 브리핑을 통해 "내가 못 읽었다"로 납득되는가.

이 세 가지가 바둑알 그래픽으로도 느껴지면 성공. 느껴지지 않으면 그래픽을 올려도 소용없다.

## 2. 목표 (Goals)

- 브라우저에서 실행되는, **한 경기(약 10분)를 처음부터 끝까지** 플레이할 수 있는 프로토타입
- 상대 팀이 유저의 개입과 경기 상황에 **반응**할 것 (아래 §8 상대 감독 AI)
- 경기 종료 후 **참모 브리핑** 화면까지 포함한 완결 루프
- 밸런스 수치와 장면 데이터를 **코드 수정 없이 JSON만으로** 조정 가능할 것

## 3. 비목표 (Non-goals) — 절대 구현하지 말 것

- 3D 그래픽, 애니메이션 캐릭터, 상단 무대/하단 레이더 이중 화면 (→ 본 개발 단계. 지금은 바둑알 단일 뷰)
- 스토리 모드, 컷신, 튜토리얼
- 멀티플레이, 고스트 대전, 서버
- 선수 성장, 이적, 재정 등 매니지먼트 요소 전부
- 참모 성장/신뢰도 진행 시스템 (참모는 고정 능력으로 등장)
- 사운드, 모바일 대응, 세이브 시스템
- 게임 엔진(Godot/Unity) — 재미 검증 후 이식한다

Claude Code가 "이것도 있으면 좋겠는데"라고 판단되는 기능은 구현하지 말고 `IDEAS.md`에 한 줄로 적어둘 것.

## 4. 기술 스택 · 아키텍처 원칙

- 바닐라 HTML/CSS/JS (ES 모듈). 프레임워크·빌드 도구 없음. `index.html` 하나로 열려야 한다.
- **코드/데이터 분리**: 장면·카드·멘트·참모는 전부 `/data/*.json`. 디자이너는 JSON만 만진다.
- **좌표 단일 원본**: 22개 바둑알의 위치는 피치 좌표(x:0–100, y:0–100) 배열 하나가 유일한 원본이다. 렌더러는 이것을 읽기만 한다. (향후 무대/레이더 이중 뷰가 이 원본 하나를 공유하게 될 것이므로, 렌더러에 상태를 두지 마라.)
- **웨이포인트 방식**: 바둑알의 움직임은 물리/AI 시뮬레이션이 아니다. 각 장면(scene)이 관련 바둑알들의 웨이포인트 경로를 데이터로 갖고, 엔진은 그것을 보간 재생한다. 장면에 관여하지 않는 알들은 소속 진형 기준점 주변을 느리게 부유(idle drift)시킨다. **실시간 축구 시뮬레이션을 시도하지 마라. 이 게임은 연출을 재생하는 게임이다.**
  - *(개정 2026-07-14)* 움직임의 **표현 레이어**는 [motion_engine_plan.md](motion_engine_plan.md) v0.2가 정본이다: "연출 재생" 원칙은 유지하되, 재생이 축구답게 읽히도록 속도 상한·진형 블록·공 물리를 갖춘 운동학으로 교체 (디자이너 지시: "공의 중력" 컨셉 폐기).
- 게임 로직은 순수 함수 위주로 분리해 콘솔에서 헤드리스 시뮬(1000경기 돌려 득점 분포 확인)이 가능하게 할 것.

- 카드 UI는 항상 노출. 개입권이 없으면 비활성.

## 6. 경기 구조 · 페이싱

- 한 경기 목표 실시간 **8–12분** (배속 1x 기준 10분). 배속 2x/4x 토글 제공.
- 경기 = 장면(scene)의 연쇄. **전반 7장면 + 후반 8장면**을 기본으로 하되 상태에 따라 ±2.
- 장면 하나의 리듬: 바둑알 흐름 재생(10–20초) → 결과 판정 → 연출 → 다음 장면. 평균 30–35초.
- 장면 결과 분포 목표치(헤드리스 시뮬로 검증): 득점 20–25% / 유효슈팅·선방 40% / 흐름 장면(압박, 볼 순환, 파울 등) 35%. **모든 하이라이트가 골이 되면 안 된다. 놓치는 장면이 경기의 질감이다.**
- 경기 스코어 분포 목표: 평균 총득점 2.5–3.5골, 0:0도 5:1도 가끔 나올 것.

## 7. 상태 기계 · 장면 선택

경기 상태(matchState) — 이것이 게임의 심장이다:

```js
{
  minute, score: [h, a],
  momentum: -3..+3,        // 흐름. 장면 결과가 누적
  lineHeight: "low|mid|high",   // 유저 카드로 변경
  tactic: "balanced|attack|counter|park",  // 유저 카드로 변경
  morale: 0..100,          // 독려 카드, 득실점으로 변동
  manAdvantage: -1|0|+1,   // 퇴장 이벤트
  opponent: { lineHeight, tactic }  // 상대 감독 AI가 변경
}
```

- 각 장면은 **태그**를 갖는다 (예: `["home_attack","left_flank","requires:momentum>=1","counter_of:opp_press"]`).
- 다음 장면은 현재 상태로 풀을 필터링한 뒤 **가중 랜덤**으로 뽑는다. 스코어·모멘텀은 하드 분기가 아니라 **가중치에만** 영향을 준다 (지고 있으면 공격 장면 확률 상승 등).
- 유저의 카드는 장면을 고르는 것이 아니라 **상태를 바꾸고**, 바뀐 상태가 다른 풀에서 뽑게 만든다. ("프리셋이 바뀌는 게 아니라 흐름의 틀이 바뀐다")
- **재맥락화**: 같은 장면도 캐스터 멘트가 스코어/시간/모멘텀의 함수로 달라진다. 멘트 데이터에 조건 필드를 둘 것. 초기 장면 풀 20–25개 + 멘트 층으로 체감 수백 장면을 만든다.

## 8. 개입 시스템 · 상대 감독 AI

**개입권**: 전반 시작 시 2, 후반 시작 시 2 지급. **전반 미사용분은 후반으로 이월.** 교체는 별도 3회(축구 규칙). 카드는 장면 재생 중 아무 때나 발동 가능 — 발동 즉시 현재 장면을 중단/완주 후 컷인.

**카드 4종 (프로토 고정)**
| 카드 | 효과 | 리스크 |
|---|---|---|
| 라인 조정(올리기/내리기) | lineHeight 변경 | 올리면 뒷공간 피격 장면 가중치 상승 |
| 전술 변경 | tactic 변경 (4종 로테이션 아님, 선택 UI) | 적용 후 2장면 동안 "적응 페널티" |
| 독려 | morale +20 | 경기당 효과 체감(2회째 +10) |
| 교체 | 지친 슬롯 교체, morale +5 | 3회 제한 |

**상대 감독 AI — "상대가 반응한다"의 실체.** 규칙 5개면 충분하다:
1. 지고 있고 70분 이후 → tactic을 attack으로, 라인 올림
2. 이기고 있고 75분 이후 → park, 라인 내림
3. 퇴장자 발생 → 수비 강화 (※ 유저가 가만히 있으면 오히려 공략이 어려워지는 아이러니가 여기서 나온다. 의도된 설계다)
4. 유저가 라인을 올리면 → 확률적으로 counter 전환
5. momentum이 -3에 도달 → 시간 끌기 장면 가중치 상승

상대의 전술 변경도 캐스터 멘트로 유저에게 **보인다** ("상대 벤치가 움직입니다"). 정보를 숨기지 마라 — 읽고 대응하는 게임이다.

### 8-B. 지시 전달 모델 *(개정 2026-07-14, Jiwon 지시: "하스스톤처럼 패를 내는 동작 — 효과는 다음/나중 시퀀스에 도착, 교체는 즉시")*

카드 발동은 **접수**(컷인)와 **도착**(효과 적용)으로 분리된다. 벤치의 지시가 그라운드에 스며드는 시간이 곧 카드의 무게다.

| 카드 | 도착 (`delivery.scenes`) | 근거 |
|---|---|---|
| 교체 | **0 — 즉시** | 교체는 절차다. 그 선수가 활약하는 건 다른 이야기 |
| 독려 | 0 — 즉시 | 외침의 정신적 효과는 즉발 |
| 라인 조정 | **1 — 다음 장면부터** | 라인 전체가 지시를 소화하는 반 박자 |
| 전술 변경 | **2 — 다다음 장면부터** | 구조 변화는 늦게 도착한다. 도착 후 적응 페널티 2장면(기존 규칙) |

- **counter 창은 발동 즉시 유효(불변).** §8의 "판정 전 발동 시 효과 테이블 교체"는 벤치의 외침에 대한 그 장면의 즉각 반응이다 — 츠바사의 순간을 지연시키지 않는다. 지연되는 것은 **상태**(장면 풀 가중치·형상)뿐이다.
- **도착은 보인다**: 도착 장면 시작 시 캐스터 텔레그래프("수원의 라인이 올라갑니다"). 대기 중에는 카드 UI에 "전달 중" 표시. 정보를 숨기지 마라.
- 상대 감독 AI 규칙 4(유저 라인 업 → counter 전환)는 **도착 시점**에 발화한다 — 상대는 라인이 실제로 움직이는 것을 보고 반응한다.
- 발동 검증(라인이 이미 끝 등)은 **대기 지시를 포함한 예상 상태** 기준. 대기 중 반대 지시도 허용된다(혼선의 대가는 개입권).
- 수치는 전부 `data/cards.json`의 `delivery` 필드 (§15 원칙).

## 9. 판정 · 연출

- **PRD 판정**: 확률 판정 실패마다 다음 판정 실효 확률 +9%p 누적, 성공 시 초기화, 상한 95%. 장기 빈도는 표기 확률에 수렴해야 한다(헤드리스 시뮬로 검증). 디버그 패널에 기본P/보정/실효P/주사위를 항상 표시.
- **판단/실행 분리**: 기대값 60% 이상의 선택이 실패하면 반드시 한 줄 — "선택은 옳았습니다. 결과가 등을 돌렸을 뿐." 유저의 분노를 참모가 아닌 운/선수에게 분산시키는 장치다.
- **정보 선행**: 결과의 단서(함성/탄식 멘트)가 연출 애니메이션보다 **먼저** 출력된다. 연출은 확인 절차다. 모든 연출은 클릭 스킵 가능.
- **3티어 연출**: 일상 장면=메시지 1줄(0.5초) / 흐름 전환=배너(1.5초) / 골·퇴장·경기종료=풀 컷인. 같은 풀 컷인은 한 경기 2회 이상 금지.

## 10. 참모 시스템 (프로토 범위)

경기 시작 전 참모 1인 선택. 프로토는 2인 — **표현과 정확도의 트레이드오프 검증용**:

| | 김성주 | 유클리드 |
|---|---|---|
| 얼굴 신호 | 크고 요란함 (3단계: 관전😐/감지😲/긴급🔥 — 프로토는 이모지/텍스트로 대체 가능, 교체 가능한 에셋 슬롯으로) | 미세함 (관전/태블릿에서 고개 듦/일어섬) |
| 텍스트 힌트 | 모호 ("왼쪽이 이상한데요?!") | 정확 ("좌측 풀백 시작 위치 +12m. 측면 보강 성공률 74%") |
| 신호 타이밍 | 장면 시작 직후 | 장면 시작 1비트 뒤 (분석 시간) |

참모 신호는 3단계로 통일하고 **표현만** 참모별로 다르게. 신호는 "개입하기 좋은 창"이 열렸을 때 발화한다 (해당 장면에 counter 카드가 정의되어 있을 때).

## 11. 경기 후 브리핑

- 참모가 경기 로그를 읽고 **최대 3개 항목**을 짚는다.
- **반사실 발언은 로그에 근거가 있을 때만**: 장면 데이터에 정의된 counter 카드가 존재했는데 유저가 쓰지 않은 순간만 "그때 ~했다면"이라고 말할 수 있다. **시스템이 검증할 수 없는 조언을 지어내지 마라.** 브리핑이 거짓말을 하는 순간 게임의 신뢰가 무너진다.
- 잘한 개입도 1개 이상 짚을 것 (적중한 카드).
- 브리핑 화면에서 "한 경기 더" 버튼 → 즉시 재시작.

## 13. 마일스톤 — 각 단계가 실행 가능해야 한다

1. **M1**: 바둑알 22개가 피치에 서고, 장면 3개가 웨이포인트로 재생되며 경기 시계가 돈다 (입력 없음)
2. **M2**: 카드 4종 + 개입권 + 상태 기계 + 상대 감독 AI — 개입하면 장면 풀이 실제로 바뀐다
3. **M3**: PRD 판정 + 3티어 연출 + 컷인 + 캐스터 재맥락화 + 정보 선행
4. **M4**: 참모 2인 + 신호 시스템 + 경기 후 브리핑 → **여기서 디자이너 1차 플레이테스트**
5. **M5**: 장면 풀 20개+ 확충, 헤드리스 시뮬로 스코어 분포 검증, 수치 조정 패스

## 14. 검증 체크리스트 (디자이너가 M4 이후 스스로 답할 것)

- [ ] 카드를 "언제 쓸지" 고민하는 순간이 있었는가
- [ ] 참모의 신호를 거슬러본 적이 있는가 (있어야 정상)
- [ ] 5실점 경기가 "운이 나빴다"가 아니라 "내가 못 읽었다"로 느껴졌는가
- [ ] 10분이 길게 느껴졌는가 (길면 장면 수 축소)
- [ ] 브리핑을 읽고 "한 경기 더"를 눌렀는가

## 15. 열린 결정 (플레이테스트로 조정할 수치)

개입권 수(4)와 이월 규칙 / 장면 수(7+8) / PRD 스텝(+9%p) / 득점 분포(20–25%) / 배속 기본값 / 적응 페널티(2장면). 전부 JSON 상수로 노출할 것.
