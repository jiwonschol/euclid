## §0.5. 기존 확정 규칙 재기재 (위반 금지)

v0.1에서 이번 작업이 **그대로 유지해야 하는** 합의:

- **연출 재생 게임이다.** 장면(scene)이 "무엇이 일어나는가"를 각본으로 정하고 판정 테이블이 결과를 정한다. 모션 엔진은 "어떻게 움직여 보이는가"만 담당한다. → v0.1 §4의 "실시간 축구 시뮬레이션 금지"는 **전술 AI 시뮬레이션 금지**로 해석을 유지하고, 움직임의 물리적 그럴듯함(속도·관성·공 비행)은 이번에 도입한다. 이것이 디자이너 지시와의 양립 해석이다.
- **좌표 단일 원본**: 22개 알 + 공의 위치는 엔진이 계산한 배열 하나가 유일한 원본. 렌더러는 읽기만 한다 (상태 금지).
- **코드/데이터 분리**: 모든 튜닝 수치는 `data/config.json`. 디자이너는 JSON만 만진다.
- **순수 엔진**: 모션 모듈은 DOM을 모른다. 헤드리스(node)에서 스텝 실행·검증 가능해야 한다.
- **판정 불가침**: `match.js`·`outcome.js`·`prd.js`·`sceneSelector.js`·`conditions.js`·`briefing.js`·`opponentAI.js`·`rng.js`·`sim/headless.mjs`는 수정 금지. 모션은 판정에 어떤 영향도 주지 않는다.
- **비목표 §3 준수**: 3D·애니메이션 캐릭터·사운드 등 금지. 추가 아이디어는 `IDEAS.md`에 한 줄로.
- **장면 전환 = 컷** 컨벤션 유지: 하이라이트 편집처럼 암전(0.9s) 후 새 배치에서 시작. 장면 사이를 연속 이동으로 잇지 않는다 (단, 컷 직후 배치는 §2.3 앵커 프레임과 정합해야 한다 — "컷마다 진형 리셋"이 진형 붕괴 인상을 지우는 장치이기도 하다).

## §1. 현재 구조와 실패 원인 (탐색 근거)

모든 문제는 `js/engine/waypoints.js` 한 파일에 있다. 판정·데이터는 건전하다.

1. **세그먼트 균등분할** — `pathAt()` (waypoints.js:21-27): 웨이포인트 경로를 거리와 무관하게 시간 균등분할. 3u 세그먼트와 40u 세그먼트가 같은 시간 → 같은 알의 속도가 세그먼트 경계마다 널뛴다. 속도 상한 자체가 없다.
2. **공 중력장** — `computePositions()` (waypoints.js:60-98): 비관여 알의 목표를 매 프레임 `앵커→공 방향 pull`로 재계산해 **즉시 배치**. 속도 개념이 없어 공이 패스로 20u/s를 날면 근처 알들도 같은 속도로 미끄러진다(지적 ④). `maxPull: 20`(피치의 1/5)이라 진형에서 20u까지 끌려나오고(지적 ②), 수비측은 `maxPressLerp: 0.8`로 공 위치까지 80% lerp — 전원 공 추격 배치가 된다.
3. **공 균등분할** — `ballAt()` (waypoints.js:104-131): 공 엔트리도 duration 균등분할. 15초 장면에 엔트리 3개면 패스 하나가 5초(공이 기어감). 부착 시 소유자 좌표에 정확히 겹침 — 터치·리드·로프트·감속 개념 없음(지적 ③).
4. **퇴장자 참조 엣지** — 퇴장한 알이 이후 장면의 공 소유자로 지정되면 `?? [50,50]` 폴백으로 공이 센터로 순간이동 (waypoints.js:123, IDEAS.md #7). 이번에 수정.

**데이터는 무죄라는 계측**: 25개 장면 전수 계측 결과 배우 필요 평균속도 최대 6.2u/s(`opp_corner/a3`, 75u/12s), 균등분할로 인한 순간속도 최대 10.3u/s. 즉 장면 데이터는 실제 축구 속도 범위 안이고, **보간·중력장 레이어만 교체하면 된다.** scenes.json 대수술은 불필요.

공 동사 사용 현황 (하위호환 유지 대상): `attach`(알 id 그대로) 61회, `shot:` 17회, `pass:` 14회, `cross:` 9회, `point:` 5회.

## §2. 모션 엔진 v2 설계

### 2.0 원칙: stateless 보간 → stateful 운동학

현행 `computePositions(ctx, t)`는 시간의 순수함수라 속도 제한이 불가능하다. v2는 **위치+속도를 가진 상태를 dt로 적분**하는 스텝 시뮬레이션으로 바꾼다. 모든 알은 "목표점을 향해 가속/감속 상한 안에서 이동"하며, 목표점이 아무리 빨리 움직여도 알은 자기 속도 상한으로만 따라간다. 이 한 문장이 지적 ①②④의 구조적 해결이다.

- 새 모듈 `js/engine/motion.js` (순수, DOM 없음):
  - `createMotion(scene, formations, matchState, cfg)` → 모션 상태 (장면 시작 배치 포함)
  - `stepMotion(motion, dtSec)` → 내부 상태 갱신, `motion.positions` = `{ h1..a11: [x,y], ball: [x,y], ballZ: 0..1 }`
- `waypoints.js`는 삭제하고 main.js 임포트를 교체한다.
- **미터 공간 운동학**: 피치 좌표는 x:0-100(≈105m), y:0-100(≈68m)로 비등방이다. 속도·거리 계산은 `METER_SCALE = [1.05, 0.68]`로 미터 환산해 수행하고, 위치는 계속 0-100 좌표로 저장한다. 이로써 config의 속도 수치가 **현실 축구의 m/s 그대로** 읽힌다 (디자이너 튜닝 직관성).
- **결정론**: 모션은 경기 rng(`match.rng`)를 절대 소비하지 않는다 (소비하면 같은 시드의 판정 시퀀스가 바뀐다 — G6 게이트로 봉인). 미세 노이즈는 현행처럼 알 id 해시 위상 + 경과시간 기반.

### 2.1 선수 운동학 (모든 알 공통)

| 파라미터 | 값 (config `motion.player`) | 근거 |
|---|---|---|
| sprint | 8.3 m/s | 실제 선수 전력질주 8-9.5 |
| run | 6.5 m/s | 압박·추격 |
| jog | 3.8 m/s | 진형 조정 |
| walk | 1.5 m/s | 유휴 |
| accel | 5.5 m/s² | 저크 방지 (0→sprint 1.5초) |
| reactionSec | 0.15-0.35 (id 해시 분산) | 목표 변경 시 반응 지연 — "전원 동시 반응" 제거 |
| arrivalRadius | 1.2 m | 도착 감속 (목표 주변 진동 방지) |

이동 모델: 목표점 추적(seek + arrival). 방향 전환은 accel 상한을 거치므로 급반전이 자동으로 둥글어진다.

### 2.2 배우 (웨이포인트 참가자)

- 경로를 **호 길이 기준 등속** 파라미터화: 알의 순항 속도 = `min(경로 총 길이 / duration, sprint)`. 세그먼트가 짧든 길든 속도가 일정하다 (지적 ① 해결).
- 필요 속도가 sprint를 넘는 장면은 알이 늦게 도착한다(클램프). 린트가 해당 장면을 지적하면 그 장면의 duration/웨이포인트만 미세 수정한다 (계측상 현재 0건 예상).
- 퇴장자 리매핑: 장면 인스턴스화 시점에 웨이포인트/공 엔트리의 퇴장 알 id를 같은 팀의 필드 위 최근접 알로 치환 (§1.4 엣지 해결).

### 2.3 비관여 알 — "공 중력" 폐기, "블록 시프트"로 교체 *(v0.3에서 §2.3-B로 대체됨)*

*(v0.2의 블록 시프트 ±8은 디자이너 판정 결과 "제자리 진동" 수준 — 기록용으로만 남긴다. 압박자 1인·jog 상한·유휴 흔들림 원칙은 §2.3-B로 승계.)*

### 2.3-B 축구 형상 모델 (v0.3) — 경기의 지리는 볼과 점유가 정한다

**근거가 되는 실축구 기하학** (트래킹 데이터·전술 문헌의 정량 사실):
- 필드 플레이어 20명은 최후방~최전방 **약 45-55m 창** 안에 함께 있다. 나머지 절반은 빈 공간이다.
- 수비팀 블록: 세로(팀 길이) 25-35m, 가로 ~40-45m로 압축, 블록 중심이 공 y를 따라 슬라이드(게인 ~0.5).
- 공격팀: 수비 라인이 **하프라인까지** 전진해 머문다(rest defense — 오프사이드가 상대 진영에서만 적용되므로 그 이상은 안 올라간다). 윙어는 터치라인까지 벌린다. GK도 페널티박스 위까지 전진(스위퍼).
- 이 형상 전체가 볼 위치를 따라 τ≈2-3s로 출렁인다. 수비 라인은 공보다 15-20m 골문 쪽을 유지한다.

**모델**: 매 스텝, 팀별로 **두 라인**(최후방 backLine, 최전방 frontLine — 자기 골문으로부터의 거리 d, x단위≈m)을 계산하고, 필드 플레이어를 그 사이에 사상한다.

- `d_ball` = 자기 골문에서 공까지 거리 (홈: ballX, 원정: 100−ballX).
- **수비 측** (장면 side의 반대팀): `back = clamp(d_ball − buffer(18), 6, 45)` / `front = min(back + length(28), d_ball + 8)` / 폭계수 0.62 / 블록 중심 y = 50 + (ballY−50)×0.5.
- **공격 측**: `back = clamp(d_ball − restBuffer(24), 14, 48)` ← **48 = 하프라인 캡, "중앙선 끝까지"의 구현** / `front = 상대 backLine의 x − 1.5` (오프사이드 라인 준수, back+26 이상 보장) / 폭계수: 빌드업 0.95, 파이널서드(d_ball>60) 1.12 (윙어 y 극단) / 중심 y 게인 0.25.
- **중립 장면**: 양 팀 모두 `back = clamp(d_ball − 20, 10, 40)`, length 30, 폭 0.85.
- **알별 사상**: depthRank = 진형 기준점 x의 팀 내 정규화 순위(DF≈0, MF≈0.5, FW≈1, formations.json에서 1회 계산). 앵커 x = lerp(backX, frontX, rank), 앵커 y = 블록중심 + (기준 y − 50)×폭계수, [3, 97] 클램프.
- **카드 연동** (기존 lineShiftX/tacticShiftX 키 폐지 → `motion.shape`로 통합): lineHeight low/mid/high = 자기 backLine −5/0/+5. tactic: attack {back+3, 폭+0.06} / counter {back−3} / park {back−6, length−4} / balanced {}.
- **스무딩**: 라인 값 자체를 τ=2.5s로 이징(알별 지터 유지). 장면 컷 시에는 새 장면의 초기 볼 위치로 라인을 **즉시** 초기화(컷 = 재배치 관행).
- **속도 상한 갱신**: 블록 알은 앵커까지 거리 ≤8m면 jog(3.8), >8m면 run(6.5) — 실축구도 재정렬은 뛰어서 한다. 공 비행과의 동조 금지는 G4′로 계속 봉인.
- 압박자 1인 규칙·GK 추종(수비 GK)·유휴 흔들림은 v0.2 그대로 승계. 공격 GK는 backLine×0.3만큼 전진(최대 x≈18, 스위퍼).

### 2.4 공 물리 (질감의 실체)

공은 상태 기계 `{attached, pass, lofted, shot, loose}`. 기존 데이터 동사와의 매핑: 알 id=`attached`, `pass:`=지상 패스, `cross:`=로프트, `shot:`=슛, `point:`=루즈볼 이동.

| 상태 | 속도 (config `motion.ball`) | 표현 |
|---|---|---|
| attached | 캐리어 속도 | 캐리어 진행방향 앞 0.8-1.6m에서 터치 리듬(위상 진동)으로 밀었다 따라잡기 — 드리블 질감 |
| pass | 16-22 m/s (거리 비례) | 직선, 마찰 감속 -3 m/s² |
| lofted | 수평 14-18 m/s | 포물선 `ballZ = 4h·t(1-t)` — 렌더러가 크기·그림자로 표현 |
| shot | 27-33 m/s | 골문 지점(y 46-54, 해시 분산)으로 직선 |
| loose | 초속 후 마찰 -6 m/s² | point: 이동, 클리어 등 |

- **비행 시간 = 거리/속도 (물리 시간)**. 균등분할 폐기. 공 스크립트 컴파일: 엔트리 경계(균등 분율)는 "이 시점쯤 전개된다"는 저작 의도로 존중하되, 이동형 엔트리는 경계 시각에 **발사**되어 물리 시간만큼 날고, 남는 시간은 도착지 attach 대기(dwell)로 채운다. 비행이 세그먼트를 넘치면 다음 attach 시간에서 차감하고, 장면 끝을 넘치면 린트가 지적한다.
- 패스 타겟 리드: 수신 알의 **도착 시점 예상 위치**로 1회 반복 조준 (움직이는 수신자를 향해 공이 미리 간다).
- 공은 절대 순간이동하지 않는다 (장면 시작 컷 제외) — G5로 봉인.

### 2.5 렌더러 (최소 변경)

- 공: `ballZ`에 따라 반지름 스케일(1 + 0.5z)과 그림자(타원, z에 비례한 오프셋/블러) — 로프트 질감. 지상 공은 현행 흰 점 유지.
- 알 렌더링은 현행 유지 (비목표: 예쁘게 만들지 마라). 방향 표시·꼬리 등 추가 금지.
- 피치 캔버스가 부모 크기를 그대로 채워 화면 종횡비가 105:68과 다를 수 있는 문제는 **이번 범위 밖** (수치상 왜곡 ≤1.5배, 프로토 허용. IDEAS 후보).

### 2.6 main.js 통합

- `computePositions` 임포트 제거 → `createMotion`(beginScene 시) + `stepMotion(dt × play.speed)`(frame 루프, `playing` 페이즈에서만).
- `frozen`(컷인) 중에는 스텝하지 않고 마지막 positions를 그린다 (현행 동작 유지).
- 배속은 dt 스케일로 일괄 적용 — 모든 운동이 비율 유지한 채 빨라진다.

## §4. 게이트 — 수치로만 판정

`node sim/motion-lint.mjs` — 전 장면(25개) × 상태 3종(중립 / momentum -3·수비 / attack·라인 high) × 장면당 duration+5s, dt=1/30s 스텝으로 샘플링:

- **G1 속도 상한**: 필드 알 순간속도 ≤ 8.8 m/s (sprint×1.06). 위반 프레임 0.
- **G2 저크 금지**: 순간 가속 ≤ 12 m/s². 위반 0 (순간이동·급반전 봉인).
- **G3 진형 유지**: 비관여·비압박 알 ↔ 시프트된 앵커 거리 p99 ≤ 7m, 최대 ≤ 10m.
- **G4′ 공-선수 분리** (v0.3 갱신): 공 비행(>12 m/s) 중 비관여·비압박 알 — 앵커까지 ≤8m인 알은 ≤ 4.2 m/s, >8m(재정렬 중)인 알도 ≤ 6.7 m/s(run+여유). 위반 0. ("공 따라 미끄러짐" 봉인은 유지하되, 라인 스윙 재정렬 질주는 합법화)
- **G8 형상 게이트** (v0.3 신설, 장면 side≠neutral·t≥4s 정상상태 샘플):
  - G8a 공격 라인 전진: 공격팀 backLine 실측(수비수 알 x의 최소/최대 적절 방향) ≥ min(44, d_ball − 30). p99 위반 0 — **"양 진영에 서 있는" 그림의 직접 봉인.**
  - G8b 수비 압축: 수비팀 필드 알의 팀 길이(전후 폭) ≤ 33m. p99.
  - G8c 전원 밀집: 필드 플레이어 20명의 x-스팬 ≤ 56. p99.
  - G8d 볼사이드 슬라이드: 수비 블록 중심 y − 50이 (ballY−50)×0.5와 같은 부호이고 오차 ≤ 8m. p95.
- **G5 공 물리**: pass/shot 비행 속도 ≥ 14 m/s / attached 중 캐리어 거리 ≤ 2.2m / 프레임간 공 이동량 > (속도×dt×2 + 0.5m) 0건 / shot: 엔트리는 공이 골문 1.5m 내 도달.
- **G6 게임플레이 불변**: `npm run sim` 게이트 전부 그린 유지 (평균 총득점 2.5-3.5, 분포 20-25/40/35, PRD 수렴) — 판정 파일 diff 0 + 같은 시드 10경기 스코어 시퀀스 구현 전후 동일.
- **G7 성능**: 22알 스텝 1000회 < 50ms (node).

폐기 기준 (착수 전 선언): G1-G5를 만족시키려다 장면 연출 의도(웨이포인트 도달)가 깨지는 장면이 5개를 넘으면, 스텝 시뮬 접근을 폐기하고 "속도 클램프를 얹은 보간" 절충안으로 후퇴한 뒤 디자이너에게 보고한다.

## §5. 가정 (이견 있으면 말해줄 것)

1. 장면 전환은 계속 **컷**이다 (연속 이동 아님). 하이라이트 편집 문법 — v0.1 합의 유지.
2. 압박자 1인 규칙은 판정에 영향 없는 **순수 표현**이다. 압박자가 붙어도 각본(패스 성공 등)은 그대로 진행된다 — 실축구 중계에서도 압박당하며 패스한다.
3. config의 속도 수치는 실측 축구 값에서 시작하되, 최종 튜닝은 디자이너 몫 (전부 JSON 노출).
4. "쓸만한 정도"의 이번 범위 = 모션. 카드/장면 콘텐츠 확충은 §7 비전 노트로 분리.

## §6. 검증 분리 선언

- 수치 게이트(G1-G7)는 헤드리스로 자동 판정한다.
- **움직임의 "질감"(공 터치 리듬, 블록이 기우는 맛)은 수치로 완결 판정할 수 없다** — 스크린샷·실행 확인 후에도 최종 판정은 디자이너 플레이(eyeball)로 분리 보고한다.

## §7. 비전 노트 (이번 범위 밖 — 다음 반복의 나침반)

디자이너 확정 방향 (2026-07-14): **캡틴츠바사의 선택권 × 하스스톤의 카드 시스템 × 쉬운 FM.**

- 츠바사 선택권 → 장면 중 "지금 이 순간"의 개입 판단 (현행 counter 창의 강화·가시화 방향)
- 하스스톤 카드 → 카드 4종 고정을 넘어선 덱/코스트/희귀도 구조 (현행 개입권=마나의 원형)
- 쉬운 FM → 매니지먼트는 게임이 대신하고 벤치의 순간만 남긴다 (v0.1 §0 정의 그대로)

모션이 축구답게 읽히기 전까지 이 확장은 착수하지 않는다 (순서 논리: 기반 신뢰 먼저).
